# How t3agent37 works

Internals. For what t3agent37 is and how to install it, see the [README](../../../README.md).

```
T3 Code ──ws──> localhost proxy (t3agent37) ──https/wss + key──> Agent37 edge ──> T3 server on an Agent37 VM
                    │                                                                └─ watchdog: decides when it sleeps
                    └─ Agent37 API: create / start / sleep / resize / exec / delete
```

- **Machine**: an Agent37 VM (`agent37-ubuntu`: Ubuntu with Docker) running the T3 server pinned to your desktop app's version, on `0.0.0.0:3773` inside the VM. The VM has no public address: Agent37's edge reaches it at `https://{id}-3773.agent37.app` only for requests that carry the workspace key (`X-Agent37-Key`), which the proxy adds, and T3's own pairing auth comes on top. The key lives on this computer only (`agent37.rs`), never on a machine: a workspace key can create and delete machines and spend the wallet.
- **Boot** (`machine/provision.sh`): the VM has no init system (PID 1 is Agent37's own; the image's entrypoint starts only dockerd and its desktop), and only `/root` is the billed, persistent disk. Docker's restart policy is what runs on every boot, so a container holding nothing but the image's static busybox (`docker import`, no download) enters the VM's namespaces with `nsenter` and runs `~/.t3agent37/boot.sh`, which keeps T3 and the watchdog running. Claude Code, Codex and gh install into `/root/.local/bin`. Claude Code's attribution (the `Co-Authored-By` trailer, "Generated with Claude Code", the session link) is turned off in `/root/.claude/settings.json`, unless that file already sets `attribution` or `includeCoAuthoredBy`.
- **Proxy** (`src/proxy`): one `http://localhost:<port>` per machine; that is the address T3 Code pairs with, so a new sandbox IP after resume never matters. The proxy is its own auth server towards T3 Code and uses its own long-lived token upstream.
  - Awake: frames pass through (minus `directEndpoints`, which would let T3 Code bypass the proxy). Snapshot-style subscriptions and some reads are recorded, and the images T3 Code loads are kept on this computer (`proxy/assets.rs`).
  - Asleep: answers pings, probes, config and other recorded subscriptions, and serves the shell and the chats from the state captured as the machine went to sleep, so opening a chat does not wake it. Images shown before stay visible.
  - Anything else wakes the machine: Agent37's `start` (a sleeping VM restores its memory in a few seconds, its T3 server still running; one moved to another host or to cold storage boots fresh), then the held request goes upstream, then the socket closes so T3 Code reconnects to the live server and resyncs. A message sent to a chat is accepted at once instead, since a wake can outlast T3 Code's 15 s slow-request warning: it shows as sent, wakes the machine and goes upstream before T3 Code reconnects; one the server refuses is reported as a notification. Only the side information T3 Code asks for on its own as it starts and as a chat opens (git status, branch, terminals, servers, the pull request's badge and checks, linked chats, the count of older chats, the branch list, the changed-files count) never does: it is shown as last seen, and with nothing recorded it stays unanswered until the machine wakes for something else. Worktree setup progress, a chat's preview tabs and their events are never shown from a recording (a stale one would hold Send, or close or reopen tabs). What T3 Code asks for on its own but a person also waits for is shown as last seen too, but wakes the machine when never seen: the linked machines (Send), a pull request's details (a quick merge, the checks popover), a related chat's title, the automations and the archived chats (their settings pages), the chats under "Show more", the files of a commit or of uncommitted changes, an MCP app's tool definition and resources (a click in the app, an approved download), the voice status of the machine dictation goes to (a mic click). Images never do either: one never seen on this computer shows as unavailable until the machine is next up. A finished command's output is kept the first time its row is expanded and shown from then on; one never expanded wakes the machine. Careful: any request that reaches a sleeping VM's URL wakes it, so nothing in the proxy or the app talks to a sleeping machine unless it means to wake it; an open socket to a VM that went to sleep just goes silent (the proxy drops it after 30 s).
- **Streams** (`proxy/media.rs`): device and browser-preview streams pass through while the machine runs, close codes included. T3 Code opens them with a ticket the proxy issues itself and keeps retrying while one is on screen, so a stream never wakes a sleeping machine (it answers 503) and only input in it (a click, a key) counts as using the machine: watching does not keep it up. Any other WebSocket (dictation's `/ws/voice`, and whatever T3 adds) is relayed the same way but wakes the machine: a person opened it.
- **Linked** (`machine/link.rs`, `proxy/link.rs`): with linked environments on in T3 Code (Settings → Labs), every machine is linked into the desktop app's own T3 server through the proxy, with full access as the ceiling, so agents on this computer can work on it (`delegate_task`, the thread tools) with nothing to set up. Links last 30 days; each wake renews one in its last week. The proxy leaves OAuth's `resource` out of the link's approval and token requests, so the machine's server issues the token for whatever it calls itself (since T3 0.1.12, the VM's internal address). The link's status probe is answered from the last descriptor and never wakes the machine; a tool call does, and counts as using it. The handshake that opens a link's MCP session is given 3 s by T3, less than a wake can take, so for a sleeping machine the proxy answers it itself: the call that follows waits for the wake, the machine refuses the unknown session and T3 opens a real one.
- **T3 Connect** (`machine/connect.rs`): T3's own route for other devices (its phone app, a browser), a tunnel the machine dials out to Cloudflare under a stable hostname. "Turn on" runs T3's `t3 up --connect --headless --yes` on the machine, opens its sign-in page here and waits until the machine is reachable, then turns on "Hold webhooks while offline": T3 Connect's relay keeps a webhook sent to a sleeping machine (up to 24 h) and delivers it as the machine wakes. The tunnel comes back by itself on every wake. Nothing wakes a sleeping machine for a phone: only t3agent37 on this computer wakes it. Provisioning names the machine in `/etc/machine-info`, so other devices show its t3agent37 name, not the sandbox's hostname.
- **Sign-ins and accounts** (`machine/signin.rs`): each machine signs its agents in on its own (`claude auth login`, `codex login`, `gh auth login --web`, run on the machine; the browser's callback is relayed to it over exec, GitHub's code is shown here), so machines can use different accounts. Who each is signed in as comes from T3's provider status in the recorded server config (`auth.email`, `auth.label`, and `usageLimits.windows` for the plan's limits, as T3 last checked them), and GitHub's login from `gh api user`, so the details show them without waking the machine. "Other account" and "Switch account" run the same login with the page in a private window of the default browser (Chrome, Edge, Brave, Vivaldi, Opera or Firefox, found in Launch Services' settings; Safari can't be asked, so it opens as usual with a notification saying so), so the browser's own sign-in doesn't answer for it. Over an existing login, the new one replaces it only when it finishes: Claude's and Codex's logins are waited on until they exit (their status says signed in throughout), and gh adds the new account, makes it the active one and t3agent37 signs the old one out.
- **Watchdog** (`src/machine/watchdog.mjs`, on the VM): the machine decides when to sleep, so it finishes its work and then sleeps even with the laptop closed. Idle = no agent run in flight (incl. waiting on an approval), no sustained CPU use (a build), no "stay awake", no work due within 5 minutes, and nobody using it for 5 minutes: through t3agent37, or in T3 from any other client (a phone through T3 Connect), seen as orchestration events only a person causes (opening a chat, pinning, archiving, ...). If T3 stops answering it counts as busy for at most 30 minutes; until it first answers after a boot it is starting, not failing. Before sleeping it drains: publishes a manifest of orchestration high-water marks, the proxy captures that state and acks, and the watchdog goes quiet at that sequence. Holding no key, it cannot sleep the VM itself: the VM runs with Agent37's auto-sleep on (5 minutes without traffic on its URLs, in practice a little more), and the watchdog holds that off by calling its own public heartbeat URL (port 3775, which only answers 204) every minute until it goes quiet. Then this app, seeing it, sleeps the VM through the API right away; with the laptop closed, auto-sleep takes it a few minutes later. Use from elsewhere meanwhile (a phone, an automation) calls the sleep off and the heartbeat comes back.
- **Scheduled work**: T3 runs automations, held webhook runs and an agent's resume after a usage limit on in-process timers, so on a sleeping machine they would not run, and T3 skips a daily automation it missed by over 10 minutes. The watchdog reports the next due time from T3's database; t3agent37 keeps it and wakes the machine 2 minutes ahead, for work that came due after the machine went to sleep (what came due while it ran had its chance). The watchdog then waits for it instead of sleeping. Only while t3agent37 runs: nothing wakes a sleeping VM on a timer (Agent37's crons post to an agent chat API, which `agent37-ubuntu` has none of).
- **Capture**: one shell snapshot, unfiltered, which serves every client whatever it asked to leave out; and the chats, one file each on this computer, named by thread id, thread sequence and snapshot encoding (`proxy/threads.rs`). A sleep fetches the files it is missing, most recent chat first, and deletes every other one: the files are the store, there is no index. It has 12 s for all of it, since the watchdog stops 20 s into a drain; a chat that did not make it wakes the machine when opened.
- **Capture freshness**: the proxy trusts its capture only when the watchdog confirmed going quiet at the captured sequence and Agent37's `slept_at` follows it within 2 minutes. Otherwise (laptop closed while the machine ran, so auto-sleep took it later) the first request that needs state wakes the machine once to resync. Recorded reads carry an epoch that moves on whenever an agent works or the user acts, so no outdated file or diff is served; recorded subscriptions (git status, terminals, ...) and the branch list a chat displays replay as last seen instead. The project's `t3.json`, which T3 Code reads on every chat open, follows the epoch too, so each sleep reads the recorded ones again: T3's editor saves over the file whatever it was shown, and a new thread's environment is decided from it. The automations T3 Code was shown are read again at each sleep as well: its editor saves every field of a task as it was shown. A branch search, a further page of branches and the one branch read T3 Code decides on (is this branch checked out in that worktree?) follow the epoch like any other read.
- **Expiry**: chats leave the store 3 days after they are settled, recordings 3 days after T3 Code last asked for them, images with the recording that points to them.
- **Resize**: Agent37 resizes only a running VM, which then boots fresh onto its new shape. An idle machine is moved right away and keeps its "keep awake"; a working one, or one asleep, moves at its next wake that finds it idle.
- **Upgrades**: on wake, a machine whose T3 version is older than the desktop app's, or whose provisioning scripts differ from the app's, is re-provisioned (`provision.sh` is idempotent; it restarts T3 only when something T3 runs on changed). A new T3 version also drops the recorded streams and stored chats: they are in the old server's encoding.
- **T3 Code's own update** ("Update N machines?"): `boot.sh` runs T3 under T3's service launcher (`t3 __service-launcher`, with `T3CODE_HOME=/root/.t3`), the way `t3 up` has systemd run it on other machines, so the server reports the `boot-service` self-update capability and T3 Code updates the machine along with the desktop app. The launcher starts the version `~/.t3/runtime/service-state.json` selects (provisioning writes it) with `~/.t3/service.env`'s settings (host, port, no browser; an explicit host wins over the `T3CODE_LAN` that `t3 up` writes there). An update downloads the new runtime on the machine, then the launcher backs up the database, swaps the server, selects the new version if it starts and rolls back if not, and points `~/.local/bin/t3` at it. The app takes the version the machine serves from its descriptor, and never takes a machine back to an older one (`provision.sh` won't either): T3's database doesn't follow a downgrade, and T3 refuses remote downgrades too. Provisioning waits for an update under way. T3 releases without the launcher (before 0.1.10), or whose launcher refuses to start the server, run as plain `t3 serve`, which T3 Code skips as "needs a manual update" (`~/.t3agent37/t3-mode` says which).
- **Disk**: Agent37 keeps a machine's disk until the machine is deleted, asleep or not, and keeps a week of daily backups of it; so unlike t3boat on Boat there is no snapshot at every sleep, no keep-alive wake and no restore onto a new sandbox. A machine never changes instance.
- **Costs**: `GET /v1/usage` reports the whole workspace's spend by instance and UTC day, settled hourly, deleted instances included; the app reads it every 5 minutes, along with the wallet's balance (`GET /v1/billing`).
- **Previews** (`machine/preview.rs`): a machine's port on `localhost` here, the same number when it's free, saved on its record and listened on while the app runs. Each connection opens T3's own preview tunnel on the machine (`/api/preview/tunnel?port=`, a WebSocket of raw bytes to its loopback) and pipes through it, so nothing new runs on the machine and no port opens there. Waking follows the proxy's rule: a page a person opens or reloads (a top-level navigation, `Sec-Fetch-Mode: navigate` with `Sec-Fetch-Dest: document`) wakes a sleeping machine and waits for it; anything else gets its connection closed without an answer. An answer of any kind would tell a dev server's reconnecting page that the server is back: Vite then reloads, and the reload would wake the machine every time it slept. A new connection counts as using the machine (dev servers close idle keep-alive connections within seconds, so clicks come as new ones); bytes on a long-lived one (a hot-reload socket) don't, so a page left open doesn't hold it up. The details view lists the servers T3 itself sees (`subscribeDiscoveredLocalServers`, read every 10 s or so while the view is open and the machine runs; T3 knows only what its terminals and agents started) and takes any other port by number. Agents here use `open_port`.
- **Project setup** (`machine/projects.rs`, `setup-project.sh`): once a project is cloned onto a machine and its env files are written, its T3 scripts are copied into the machine's script overrides (T3's clone leaves them behind, and a client can't change a project's own scripts), and `setup-project.sh` runs in its folder in the background. It runs the scripts set to run on worktree creation; without any, it does submodules and installs dependencies by lockfile, bringing the package manager when that is quick (Bun, corepack's pnpm and Yarn, npm, uv) and skipping big toolchains the machine lacks (Rust, Go, Ruby). Frozen lockfile first, so the checkout stays clean. Its steps show on the project's row; a failure is a notification with the log's tail, never a failed add. Off in Settings.
- **Notifications and alerts:** the watchdog names the top-level threads it sees working; when none has worked for 8 s after some did, the app says which finished (`notify_finished`). The wallet is checked against Settings' line at each costs refresh, once until it is topped up above it. A machine up without a break for Settings' hours is reported once per stretch, with what holds it up. T3 Connect's phone push (T3's own, sent by the machine) covers the laptop being closed.
- **GitHub issues** (`machine/issues.rs`, `issues.mjs`; a prototype): turning issues on for a project makes a webhook on its GitHub repo, with the machine's own gh login, that sends issue events to the machine's inbox (port 3777, in the watchdog) through a public URL of its own. A delivery wakes a sleeping machine like any request to its URLs. The inbox checks GitHub's signature against that webhook's secret (made on the machine, and kept only there and on GitHub), then acts on one event: the project's label put on an open issue by someone GitHub says can push there. That issue becomes a thread (`t3 thread start`) with the project's agent, in a new worktree on `issue-<n>` from the fetched default branch, told to open a pull request that fixes it, and the issue gets a comment saying so. Each project has its own settings: the label (`agent` at first; made in the repo if it has none) and a model of the machine's signed-in agents with its reasoning level, picked from the models T3 lists in the machine's server config (`issue_models`, never waking it) and passed as `--provider`, `--model` and `--option effort=…`. Changing them runs the same turn-on again, which keeps the webhook and its secret. Each issue is taken on once (`issues-state.json`); a start that failed is tried again when the label goes on again. GitHub doesn't retry a failed delivery, so the inbox also looks for labeled issues it hasn't taken on whenever T3 first answers after a boot and after every wake. Turning issues off removes the webhook, and the public URL with the last one; deleting the machine removes its webhooks first.
- **Projects** (`projects.rs`, `machine/projects.rs`): t3agent37 moves no code itself; it drives T3 Code's own flow through T3's API. "Add a project" (in a machine's details, or picked when creating one) does what T3's "Add to another machine" dialog does: reads the project and its `.env` files from the desktop app's server (t3agent37 holds its own read-only session there, "t3agent37" under Settings → Connections), then `projectClone.start` on the machine, which clones over HTTPS and registers the project with progress in T3 Code, then `projects.writeFile` for the env files. Private repos need the machine signed in to GitHub: "Sign in" next to GitHub in its details runs `gh auth login --web` on the machine (GitHub's device flow: the page opens here, the code is copied to the clipboard), and git uses gh as its credential helper for T3's clones and pushes. The token is created on the machine and stays there. The machine's projects are read from its shell when it runs or sleeps, so listing them never wakes it. Work goes back the way T3 Code does it: push or open a PR. Agents use `add_project` here, or T3's own tools through the link (`t3_project_clone`, `delegate_task`, `t3_thread_launch` with the machine's `environmentId`).
